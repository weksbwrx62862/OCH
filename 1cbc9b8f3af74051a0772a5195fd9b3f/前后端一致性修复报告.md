# OpenClaw-Harness 前后端一致性修复报告

**日期**: 2026-04-10  
**范围**: 前端 API 调用 ↔ 后端路由定义的一致性对齐  
**严重级别**: P0 × 2, P1 × 2, P2 × 1

---

## 一、问题总览

| # | 问题 | 严重级别 | 前端行为 | 后端要求 | 影响 |
|---|------|---------|---------|---------|------|
| 1 | StreamChat 绕过 BFF 代理 | **P0** | `apiClient.streamChat()` 直接连接 `http://${backendHost}:8008/...` | BFF 代理 `app/api/proxy/chat/route.ts` 已存在但未使用 | CORS 失败；反向代理部署断链 |
| 2 | 审计导出 `window.open()` 无法认证 | **P0** | `window.open('/api/v1/audit/export')` | `@require_role('admin')` | 始终返回 401；导出功能完全不可用 |
| 3 | Chat 自动创建 Agent 调用 admin-only 端点 | **P1** | `chat/page.tsx` 调用 `POST /agents` | `POST /agents` 需要 `@require_role('admin')` | 非管理员用户进入 Chat 时 403 |
| 4 | 登录页缺少密码字段 | **P1** | 登录表单只发 `{ username }` | 后端期望 `{ username, password }` | 开发环境侥幸可用；正式认证不可用 |
| 5 | MCP 服务器管理 admin 权限不匹配 | **P2** | 任何用户可添加/移除 MCP 服务器 | `POST /mcp/servers` 和 `DELETE /mcp/servers/{id}` 需要 admin | 非 admin 用户操作返回 403 |

## 二、修复详情

### Fix #1 — StreamChat 通过 BFF 代理（P0）

**文件**: `frontend/lib/api.ts`

**修改内容**:
```diff
- const backendHost = process.env.NEXT_PUBLIC_BACKEND_URL || `${window.location.hostname}:8008`;
- const url = `http://${backendHost}/api/v1/sessions/${sessionId}/chat`;
+ const url = `/api/proxy/chat?sessionId=${encodeURIComponent(sessionId)}`;
```

**修改原因**:  
原实现直接在浏览器中构造后端 URL（`http://host:8008/...`），存在三个问题：
1. **CORS**: 浏览器对跨域 SSE 请求有严格限制，OPTIONS 预检可能失败
2. **部署断链**: 生产环境通过 Nginx/Caddy 反向代理，前端不应知道后端端口
3. **BFF 浪费**: Next.js 已实现 `app/api/proxy/chat/route.ts` 代理路由（自动转发 Authorization 头、透传 SSE 流），但从未被调用

修改后，所有 SSE 请求通过 Next.js BFF 代理 → 后端，与其他 API 调用保持一致的请求路径。

### Fix #2 — 审计导出改为认证下载（P0）

**文件**: `frontend/app/audit/page.tsx`

**修改内容**:
```diff
- const handleExport = () => {
-   window.open('/api/v1/audit/export', '_blank');
- };
+ const handleExport = async () => {
+   try {
+     const token = localStorage.getItem('och_token');
+     const response = await fetch('/api/v1/audit/export', {
+       headers: { ...(token ? { Authorization: `Bearer ${token}` } : {}) },
+     });
+     if (!response.ok) throw new Error(`导出失败: ${response.status}`);
+     const blob = await response.blob();
+     const url = URL.createObjectURL(blob);
+     const a = document.createElement('a');
+     a.href = url;
+     a.download = contentType.includes('csv') ? 'audit-xxx.csv' : 'audit-xxx.json';
+     document.body.appendChild(a);
+     a.click();
+     document.body.removeChild(a);
+     URL.revokeObjectURL(url);
+   } catch (e) { alert('导出失败，请检查权限'); }
+ };
```

**修改原因**:  
`window.open()` 是浏览器导航行为，无法携带 `Authorization: Bearer {token}` 请求头。后端 `GET /api/v1/audit/export` 使用 `@require_role('admin')` 装饰器，没有 token 的请求直接返回 401。

改用 `fetch()` + `Blob` + 动态 `<a>` 标签下载方案：
1. 请求正确携带 Bearer token
2. 支持后端返回 JSON/CSV 两种格式（后端根据 `?format=` 参数决定）
3. 错误时友好提示而非静默失败

### Fix #3 — 新增 Agent 快速创建端点（P1）

**后端文件**: `backend/app/api/agents.py`

**修改内容**: 新增路由 `POST /agents/quick-create`

```python
@agents_bp.route('/quick-create', methods=['POST'], endpoint='quick_create_agent')
@require_auth  # 仅需登录，不需要 admin
def quick_create_agent():
    """快速创建聊天用 Agent（普通用户可用，受限参数）."""
```

关键设计决策：
- **仅 `@require_auth`**，不要求 admin 角色
- **受限参数**: 只接受 `name` 和 `model`，`system_prompt` 固定为默认值，`description` 自动填充
- **来源标记**: `config={'source': 'quick-create'}` 可区分自动创建和管理员手动创建的 Agent
- **原有端点不变**: `POST /agents` 仍然需要 admin，用于正式的 Agent 管理

**前端文件**: `frontend/app/chat/page.tsx`

```diff
- const agentRes = await apiClient.post('/agents', {
-   name: `ChatBot-${Date.now()}`,
-   description: '默认聊天智能体',
-   system_prompt: '你是一个有帮助的 AI 助手。',
-   model: 'claude-sonnet-4-20250514',
- });
+ const agentRes = await apiClient.post('/agents/quick-create', {
+   name: `ChatBot-${Date.now()}`,
+   model: 'claude-sonnet-4-20250514',
+ });
```

**修改原因**:  
Chat 页面的 Agent 自动创建是"聊天入口"功能，不应要求 admin 权限。普通用户进入 Chat 就应该能创建一个聊天 Agent，就像创建一个 Session 一样自然。原有的 `POST /agents` 端点保留 admin 权限，用于 Agent 管理页面的正式 CRUD。

### Fix #4 — 登录页添加密码字段（P1）

**文件**: `frontend/app/login/page.tsx`

**修改内容**:

1. 添加 `password` 状态:
```diff
+ const [password, setPassword] = useState('');
```

2. 请求体包含 password:
```diff
- body: JSON.stringify({ username }),
+ body: JSON.stringify({ username, password }),
```

3. 添加密码输入框 UI:
```tsx
<div>
  <label htmlFor="password">密码</label>
  <input
    id="password"
    type="password"
    value={password}
    onChange={(e) => setPassword(e.target.value)}
    placeholder="输入密码（开发环境可留空）"
  />
</div>
```

**修改原因**:  
后端 `auth.py` 的 login 接口期望 `{ username, password }` 两个参数，`password` 默认为空字符串。前端只发送 `{ username }` 虽然在当前开发环境能用（后端不校验密码），但：
1. 接口契约不一致，增加后续接入正式认证的心智负担
2. 用户无法理解为什么没有密码就能登录
3. 如果后端将来启用密码校验，前端不会发送密码导致 401

### Fix #5 — MCP 管理 UI 权限控制（P2）

**文件**: `frontend/app/settings/page.tsx`

**修改内容**:

1. 添加角色检查:
```tsx
const [isAdmin, setIsAdmin] = useState(false);
useEffect(() => {
  const userStr = localStorage.getItem('och_user');
  if (userStr) {
    const user = JSON.parse(userStr);
    setIsAdmin(user?.role === 'admin');
  }
}, []);
```

2. 条件渲染 MCP 操作按钮:
```tsx
// 移除按钮 — 仅 admin 可见
{isAdmin && (
  <button onClick={() => handleRemoveMcp(srv.id)}>移除</button>
)}

// 添加按钮 — admin 显示按钮，非 admin 显示提示
{isAdmin ? (
  <button onClick={() => setShowAddMcp(true)}>+ 添加 MCP 服务器</button>
) : (
  <p>需要管理员权限才能添加 MCP 服务器</p>
)}
```

**修改原因**:  
后端 MCP 端点的写操作（`POST /mcp/servers`、`DELETE /mcp/servers/{id}`、`PUT /mcp/servers/{id}`）均需要 `@require_role('admin')`。前端允许任何用户点击这些按钮会导致 403 错误。通过前端 UI 层面的权限控制：
1. 避免无意义的 API 调用和错误提示
2. 清晰告知用户权限不足
3. 安全纵深：前端隐藏 + 后端校验双重保障

## 四、一致性验证矩阵

修复后前后端 API 对齐情况：

| 前端调用 | 后端路由 | 权限 | 状态 |
|---------|---------|------|------|
| `apiClient.streamChat()` → `/api/proxy/chat?sessionId=` | BFF → `POST /api/v1/sessions/{id}/chat` | `@require_auth` | ✅ |
| `fetch('/api/v1/audit/export', { headers: { Authorization } })` | `GET /audit/export` | `@require_role('admin')` | ✅ |
| `apiClient.post('/agents/quick-create', ...)` | `POST /agents/quick-create` | `@require_auth` | ✅ |
| `apiClient.post('/agents', ...)` (管理页面) | `POST /agents` | `@require_role('admin')` | ✅ |
| `fetch('/api/v1/auth/login', { username, password })` | `POST /auth/login` | 公开 | ✅ |
| MCP 添加/移除（仅 admin 可见 UI） | `POST/DELETE /mcp/servers` | `@require_role('admin')` | ✅ |

## 五、后续建议

1. **E2E 测试覆盖**: 建议对以上 5 个修复场景添加端到端测试，防止回退
2. **API 契约层**: 考虑引入 OpenAPI 代码生成（如 `openapi-typescript`），从后端 Swagger 文档自动生成前端类型定义
3. **角色系统完善**: 当前角色只有 admin/user 两级，建议细化权限模型，使用 RBAC 或 ABAC
4. **BFF 代理扩展**: 审计导出也可以走 BFF 代理，避免前端直接访问后端 `/api/v1/` 路径
