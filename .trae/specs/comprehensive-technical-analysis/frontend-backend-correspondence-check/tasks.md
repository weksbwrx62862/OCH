# Tasks — 前后端功能对应关系检查

## 阶段 1: 前端 API 调用提取与后端路由匹配

- [x] **T1.1: 提取前端所有 API 调用**
  - 遍历 8 个前端页面 + api.ts + appStore.ts
  - 提取所有 `apiClient.get/post/put/delete/streamChat` 调用
  - 记录：调用位置（文件:行号）、HTTP 方法、URL 路径、期望响应类型

- [x] **T1.2: 提取后端所有 API 路由**
  - 遍历 14 个 Blueprint 文件
  - 提取所有 `@bp.route()` 装饰器定义的路由
  - 记录：Blueprint 名称、URL 前缀、路由路径、HTTP 方法、endpoint 名称

- [x] **T1.3: 前后端路由匹配验证**
  - 将前端 API 调用 URL 与后端路由逐一匹配
  - 标记：匹配成功 / 前端调用无后端 / 后端路由无前端调用
  - 输出匹配结果矩阵

## 阶段 2: 数据交互格式一致性检查

- [x] **T2.1: 响应体结构对比**
  - 对比前端 TypeScript 接口（Agent/Session/ToolInfo/Skill/Team/Config 等）与后端 jsonify() 返回结构
  - 标记字段名不一致、类型不兼容、缺失字段
  - 重点检查 Tools 页面数据格式差异

- [x] **T2.2: SSE 流式事件格式对比**
  - 对比前端 StreamEvent.type 枚举与后端 _make_sse_event() 事件类型
  - 检查 chat/page.tsx 中的 switch 分支是否覆盖所有后端事件类型
  - 检查前端类型定义是否包含所有实际处理的事件类型

- [x] **T2.3: 请求体格式对比**
  - 对比前端 POST/PUT 请求发送的数据结构
  - 与后端 request.get_json() 期望的字段进行匹配
  - 标记缺失字段、多余字段、类型不匹配

## 阶段 3: 界面元素与后端功能对应检查

- [x] **T3.1: 按钮功能绑定检查**
  - 检查所有页面的 `<button>` 元素
  - 验证 onClick 事件是否绑定了实际功能
  - 标记"空壳按钮"（有 UI 无功能）

- [x] **T3.2: 导航链接有效性检查**
  - 检查所有 `<Link href>` 路径
  - 验证目标页面文件是否存在
  - 标记死链接

- [x] **T3.3: 表单提交与后端处理检查**
  - 检查所有表单/输入框的提交逻辑
  - 验证提交数据是否发送到后端 API
  - 标记未连接后端的表单

## 阶段 4: 功能模块覆盖度分析

- [x] **T4.1: 按 Blueprint 模块统计覆盖度**
  - 对 14 个后端 Blueprint 模块逐一统计
  - 计算每个模块的后端端点总数、前端调用数、覆盖率
  - 输出覆盖度排名表

- [x] **T4.2: 识别前端"盲区"模块**
  - 列出覆盖率为 0% 的后端模块
  - 评估各模块的业务重要性和前端缺失影响
  - 提出优先级建议

- [x] **T4.3: 识别后端"冗余"端点**
  - 列出有前端页面但后端提供了更多端点的情况
  - 评估哪些额外端点应在前端暴露
  - 提出前端功能补全建议

## 阶段 5: 检查报告生成

- [x] **T5.1: 汇总所有检查结果**
  - 整合阶段 1-4 的分析数据
  - 按严重程度分类：关键问题 / 重要问题 / 一般问题 / 建议
  - 为每个问题提供：位置、描述、影响、调整建议

- [x] **T5.2: 生成前后端对应关系矩阵**
  - 创建模块 × 功能的对应关系表格
  - 标注每个交叉点的状态：✅ 已对应 / ⚠️ 格式不一致 / ❌ 缺失 / ➖ 不适用

- [x] **T5.3: 输出调整建议清单**
  - 按优先级排列所有需要调整的项目
  - 每项包含：问题描述、涉及文件、建议方案、预估工作量
