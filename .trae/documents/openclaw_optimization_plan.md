# 基于文章工作流的 OpenClaw 项目优化计划

结合文章《用 OpenClaw 搭建「多 Agent 协作系统」：架构介绍 + Obsidian 联动》中描述的核心工作流（8大脑区协作、可生长记忆、硬制动器等），当前项目在具体落地时存在以下需要优化的“偏离点”或“未闭环”问题：

## 1. “海马体（Learner）”学习闭环断裂，系统无法“生长”
- **偏差分析**：文章强调 Learner（对应项目中的 `hr_dept`）要在任务结束后“从反馈中提炼可复用认知，更新 MEMORY”。但查看 `dispatch_center/AGENTS.md` 的标准作业流，发现在“结果汇总并回复用户”后任务就直接结束了，**并未触发任何复盘机制**。
- **优化方案**：修改调度中心（main）的工作流定义，在任务完成后增加 **[知识沉淀]** 阶段。强制要求将包含错误、修正过程的任务流转给 `hr_dept`，由其提取经验并自动写入对应部门的 `MEMORY.md`。

## 2. “检索系统（Librarian）”角色严重固化，未能深度联动 Obsidian
- **偏差分析**：文章中的 Librarian 负责“找资料、整理材料”，是 Obsidian 外挂记忆的大管家。但查看 `intelligence_center/SOUL.md` 发现，其后半部分被硬编码为“你的唯一职责：每日早间采集全球重要新闻”，导致其变成了一个定时爬虫，丧失了处理通用检索任务和整理 PARA 笔记库的能力。
- **优化方案**：
  - 重写 `intelligence_center/SOUL.md`，剔除硬编码的新闻爬虫职责（将其转为独立的 Cron 脚本）。
  - 赋予该 Agent 明确调用 `obsidian_integration.py`（create/search/extract-pdf）的指令，使其真正在任务执行中承担“查询本地库”和“归档新知识”的职能。

## 3. “制动器（Review）”环节缺乏强制阻断（Human/Reviewer in the loop）
- **偏差分析**：文章规定 Review 脑区“专门挑毛病，不确定时宁可拒绝”。目前项目中的流程卡是流程式的，但代码执行逻辑（如 `task_executor.py` 和看板流转）中，Review 的结论如果是否定的，似乎缺乏自动将任务“打回重做（Reject & Retry）”的强制闭环，可能会被调度中心直接作为“最终结果”汇总给用户。
- **优化方案**：在 `AGENTS.md` 中强化 **断路器追踪** 机制。明确规定：若执行动作包含“代码修改”或“高风险操作”，必须强制加入 `review_dept`。且如果 Review 给出的状态是 `Rejected`，调度中心不得直接回复用户，必须将任务退回 `execution_dept` 重做，直到触发 3 次循环上限。

## 4. 流程卡（Flow Card）的自动降级漏洞
- **偏差分析**：目前的配置将单部门任务视为“简单任务（不生成流程卡）”。这违背了文章中“有副作用的动作必须等批准”的理念。如果用户下达“帮我删除所有旧日志”（单部门执行），系统可能会跳过审批直接执行。
- **优化方案**：在 `dispatch_center` 的 `AGENTS.md` 判断标准中，补充“意图包含增删改等副作用动作时，无论是否跨部门，必须生成流程卡并等待用户批准”的规则。
