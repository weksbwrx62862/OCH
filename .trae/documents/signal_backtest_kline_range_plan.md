# 信号回测K线范围调整实现计划

## 项目概述
当前信号预览功能中，虽然增加了K线数量的选项，但是实际图表显示的信号数量并没有变化。问题在于前端使用K线数据的时间范围来获取信号触发数据，而交易所API可能对K线数量有默认限制。

## 任务分解

### [ ] 任务1：检查交易所API K线数量限制
- **优先级**: P0
- **依赖**: 无
- **描述**:
  - 测试Hyperliquid API的K线数量限制
  - 验证不同count参数下返回的实际K线数量
  - 确定交易所API的最大限制
- **成功标准**:
  - 了解交易所API的K线数量限制
  - 验证不同count参数的实际效果
- **测试要求**:
  - `programmatic` TR-1.1: 测试不同count值下API返回的K线数量
  - `programmatic` TR-1.2: 验证时间范围是否正确

### [ ] 任务2：修改前端时间范围计算逻辑
- **优先级**: P0
- **依赖**: 任务1
- **描述**:
  - 分析当前时间范围计算逻辑
  - 修改为基于count参数计算时间范围
  - 确保信号触发数据的时间范围与K线数量匹配
- **成功标准**:
  - 前端能够根据选择的K线数量计算正确的时间范围
  - 信号触发数据的时间范围与K线数量匹配
- **测试要求**:
  - `programmatic` TR-2.1: 不同K线数量下时间范围计算正确
  - `programmatic` TR-2.2: 信号触发数据覆盖完整的时间范围

### [ ] 任务3：优化后端信号回测逻辑
- **优先级**: P1
- **依赖**: 任务1
- **描述**:
  - 检查后端信号回测的时间范围处理
  - 确保回测逻辑能够处理不同时间范围的请求
  - 优化回测性能以支持更大的时间范围
- **成功标准**:
  - 后端能够处理不同时间范围的回测请求
  - 回测性能能够支持更大的时间范围
- **测试要求**:
  - `programmatic` TR-3.1: 后端能够处理不同时间范围的回测请求
  - `programmatic` TR-3.2: 回测性能满足要求

### [ ] 任务4：测试和验证
- **优先级**: P1
- **依赖**: 任务2, 任务3
- **描述**:
  - 测试不同K线数量设置下的信号预览
  - 验证信号数量是否随K线数量增加而增加
  - 确保系统性能和用户体验
- **成功标准**:
  - 不同K线数量设置下信号预览正常
  - 信号数量随K线数量增加而增加
  - 系统性能良好
- **测试要求**:
  - `programmatic` TR-4.1: 不同K线数量设置下信号预览正常
  - `human-judgement` TR-4.2: 信号数量随K线数量增加而合理增加

## 技术实现要点
1. 测试交易所API的K线数量限制
2. 修改前端时间范围计算逻辑，确保与K线数量匹配
3. 优化后端信号回测逻辑，支持更大的时间范围
4. 测试不同K线数量设置的效果

## 预期结果
用户选择不同的K线数量时，图表显示的信号数量会相应变化，真正体现K线数量增加的效果。
